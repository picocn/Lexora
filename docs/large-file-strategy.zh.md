# 大文件打开性能优化方案（L1 + L2 + L3）

> 现状/背景：顺序打开多个超大（100MB 级）markdown 时，打开耗时随文件数超线性劣化
> （实测 100MB×11：第 1 个 ~3s → 第 11 个 ~162s），内存平台 ~4.5GB 但时间失控。

## 1. 数据与根因（实测）

### 1.1 100MB 压测（20×100MB，累计 1→20 不关闭，进程树内存）
- 打开耗时：n=1 3.1s → n=5 23.9s → n=8/9 ~20-24s → **n=10 95.8s → n=11 161.9s**；
  12 个之后单文件已超数分钟，测试在 n=11 按静默阈值安全终止。
- 内存：进程树 1.87GB(1) → 峰值 4.53GB(6-8) → 平台 ~3.7-4.2GB(9-11)；主进程仅 ~27MB，
  其余全部在 WebView2 子进程。
- 结论：内存没有“爆掉”，**时间失控**——已打开的大文档全部常驻后，每次新开文件都叠加
  GC 停顿 + 大字符串 IPC/JSON 拷贝 + 挂载遍历成本。

### 1.2 20MB 压测（20×20MB，同法，带阶段计时）
| # | open(ms) | read(ms) | lang(ms) | state(ms) |
|---|---|---|---|---|
| 1-5 | 700-900 | ~250 | 0 | 30-140 |
| 6-9 | 1030-1350 | ~240 | 0 | ~32 |
| 10-13 | 1300-2200 | ~260 | 0 | ~35 |
| 14-20 | 1700-3300 | ~240-290 | 0 | ~30-60 |

- 读文件 ~0.25s、CM 状态创建仅 30-60ms（固定小头）→ **大头在未分段部分**
  （React 提交渲染 + CM 挂载 + GC，约 0.6-3s），且随驻留文档数增长而增长。
- 进程树内存 0.88GB(1) → 3.1-3.4GB(14-20 平台化)，单文件边际 ~120-200MB。
- Node 侧单文件微基准：磁盘读+解码 0.32s；EditorState.create（纯文档）~0.58s、
  带 markdown ~0.52s；单 100MB 文档 JS 堆 ~+350MB。

### 1.3 根因
打开单个文件的“固定成本”很小；劣化来自**已打开超大文档全量常驻**造成的主线程
GC/渲染/IPC 压力。→ 解法必须限制“常驻的超大文档数量”，而不是加速单文件读取。

## 2. 方案设计

### L1 —— 使用护栏（防误操作 & 防启动卡死）
- 手动打开（对话框/最近打开）文件 > `20MB` 时弹确认框：「后台打开 / 取消」，
  并提示占用与耗时（见 `LARGE_FILE_WARN_BYTES`）。
- 会话恢复（下次启动重开上次文件）跳过 ≥ `64MB` 的文件并提示已跳过数量
  （`SESSION_SKIP_BYTES`），避免一开机就默默载入若干 GB。

### L2 —— 前台体验优化
- 确认后的大文件以**后台方式**打开：`openFile(..., focus:false)` 不抢占当前标签，
  完成后提示「已在后台打开大文件」；用户用标签栏切换（标签条支持 ‹ › + 自动滚动）。
- 超大文件（≥ `UNLOAD_BIG_CHARS`）标签**关闭撤销历史**（`noHistory`），减少无关开销。

### L3 —— 超大标签驻留上限 + 自动卸载（治本）
- 阈值：文档字符数 ≥ `UNLOAD_BIG_CHARS = 40_000_000`（约 55MB+ 文本）视为“超大”。
- 规则：常驻的超大**干净**（内容==磁盘，未保存脏标签永不卸载）标签数 ≤
  `KEEP_LOADED_BIG = 4`。
- 超出时，把最早的非活动超大干净标签 `unloadBigTab` 退化为轻量占位：
  - 同一 Tab（相同 id/标题/路径/顺序），`cmState` 换成空文档，`Tab.unloaded = true`；
  - `tabDirty()` 对 unloaded 标签恒为 false（占位即干净）；
  - 标签条上仍显示、可关闭/保存会话（session 只记路径）。
- 激活占位标签时 `onActivate` 先 `reloadBigTab`：显示「正在加载大文件…」→ 重新读盘
  （本地磁盘 ~0.3s/100MB）+ 建状态（~0.6s）+ 挂载，实测单次重载约 1.5-3s。
- 预期效果：任意数量打开超大文件时，常驻超大文档 ≈ K+（活动 1）个 → GC/IPC 压力恒定，
  单文件打开时间回归平稳、内存平台 ≤ 约 2-2.5GB。

阈值集中在 `src/tabs/thresholds.ts`，可随时调整。

## 3. 涉及改动
- `src/tabs/thresholds.ts`（新增）：阈值常量
- `src/tabs/types.ts`：`Tab.unloaded`；`tabDirty()` 忽略 unloaded
- `src/tabs/store.ts`：`openFile` 支持 `focus:false` / `noHistory`；
  `unloadBigTab` / `reloadBigTab`（原 id/顺序原地替换）
- `src/editor/cmCore.ts`：`historyExtension(noHistory)`；createEditorState 支持 noHistory
- `src/App.tsx`：
  - 打开入口拆分 `openUserFile`（对话框/最近，>20MB 先确认）→ `openLoaded`（真实打开）
  - `confirmOpenBig` 后台打开；会话恢复跳过大文件并计数提示
  - L3 容量限制 effect；`onActivate` 对 unloaded 标签先重载再激活
  - 大文件确认 Modal（复用 Modal 组件）
- 测试：`store.test.ts` 新增 focus:false / unload / reload 用例（47/47）

## 4. 已知限制 / 注意
- 预览：源编辑标签处于 unloaded 占位时，其预览标签内容为空；建议先点源标签（触发重载）。
- 重载后的撤销历史按超大文件规则关闭；languageOverride 保留（按 override 重新加载语言）。
- 卸载只针对“文件型 + 干净 + 超大”；未保存/小文件标签永远常驻。
- 卸载后若磁盘内容已被外部改动，重载会取最新磁盘内容（磁盘锚点=最新内容，视为干净）。

## 5. 复测方法与目标
用 `D:\lexora-bench`（`bench-targets.json` + `watchdog.ps1`，应用内基准通道）：
1. 20×20MB：回归对照（期望与优化前基本一致：~32s 总量、峰值 ~3.4GB，无劣化）。
2. 6×100MB（或 20×100MB 视时间）：打开到第 5/6 个时开始卸载早前标签；
   期望进程树内存平台 ≤ ~2.5GB，且第 4 个以后单文件耗时不再逐级放大。
目标指标：20×100MB 顺序打开内存 ≤ ~2.5GB、单文件耗时平稳（≤5-8s），可稳定开满 20 个。
